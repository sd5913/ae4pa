本文件统一“谁做什么、依赖谁、交付什么、怎样算完成”。它以原《Godot三周逐步分工 共享美术版 V2》为职责来源，并结合原策划案 V3 和仓库现有底座／Markdown。1.0 是仓库整合分工文档的独立版本号，源手册继续保留 V2 标识。

## 1 四个人的固定职责

| 成员 | 主要功能 | 主要修改范围 | 不直接重写的部分 |

| B 证件与员工 | 三名工作人员、背后偷窃、三卡所有权、双槽、Q 切换、装备和换卡通知 | scenes/staff/、scripts/card_manager.gd、scenes/tests/staff/ | 主角移动、主场景和 D 的菜单 |

| D 界面剧情与测试 | 菜单、说明／图鉴、HUD、背包显示、对白、失败／结局、QA 和交付材料 | scenes/ui/、scenes/tests/ui/、QA 与说明文档 | B 的卡片数据、C 的怪物判定 |

四人均承担能运行的 Godot 制作任务；美术由全员共同选择。使用者负责把选定素材导入自己的场景。A 建立公共文档和骨架，D 后续维护说明与测试记录；产品／接口变更仍由 A 组织确认。

仓库已有 work/member-1 至 work/member-4，人员对应由 A 确认，不把编号直接当成身份。现有分配优先保留；原手册中的 feat 分支名是示例。A 的当前功能分支也可以继续使用，完整流程见协作指南。

## 3 A 的任务顺序和交付标准

下列 A-01 至 A-12 对应原 V2 的 A 工作步骤；BASE 是公共底座编号，与 PLANS.md 的全项目任务编号分别使用。

| 编号 | A 要做什么 | 交付物与完成标准 |
|---|---|---|
| A-01 | 统一规范并发布公共底座 | 共享项目、按键和公共名称；B/C/D 能从同一基线开始 |
| A-02 | 制作主角独立场景 | player.tscn，左右移动、松手停止，无跳跃 |
| A-03 | 限定边界和横向相机 | 主角不走出走廊，镜头不露出地图外 |
| A-04 | 制作可复用测试走廊 | 左入口、右出口位置及员工／门／UI 接入位，先用占位图 |
| A-05 | 接 B 的偷窃和卡片 | 放入员工、连接数据与提示；卡片跨到 2F 不丢失 |
| A-06 | 接 C 的通用门 | 能在主游戏摆门、改房号／类型、接失败上报，不复制五份脚本 |
| A-07 | 五层切换 | floor_1 至 floor_5 可逐层进入，入口重定位正确，通行条件符合主策划 |
| A-08 | 309 救援与跟随 | 调用 D 对白，完成 has_friend，4F／5F 持续显示闺蜜且不独立检测 |
| A-09 | 本层失败重试 | 接 B/C 失败与 D Retry，重置本层和计时，按约定恢复卡片／故事 |
| A-10 | 菜单、五楼出口和结局连接 | 开始、重试、返回、EXIT 均走正确流程；接入所需统计数据 |
| A-11 | 每次 PR 接入后回归 | 检查文件范围、F6／F5、新旧行为和可恢复的版本记录 |
| A-12 | 最终导出与源码交付 | Windows 目标电脑可运行并通关；源项目和说明齐全，Web 按要求与余量安排 |

当前 A-01 至 A-04 的底座内容已发布并在 A 本机验证；成员验证、设置截图交接仍需记录。A-05 起依赖 B/C/D 的实际组件，不能把空目录或开发覆盖层当成已接入功能。

## 4 B 的任务顺序和交付标准

| 编号 | B 要做什么 | 交付物与完成标准 |
|---|---|---|
| B-01 | 建一名员工组件 | staff.tscn 可配置 SECURITY／CLEANER／MANAGER，共用一套场景 |
| B-02 | 定时左右转身 | 固定站位，可肉眼看到朝向变化；预告表现按主策划补充 |
| B-03 | 接近判定 | 约 55 像素内才显示偷窃提示，远处按 E 不误触发 |
| B-04 | 背后长按偷窃 | 正确一侧按住约 0.8 秒获得卡片，期间站定 |
| B-05 | 中途回头失败 | 正面尝试或被转身看到，调用统一失败入口 |
| B-06 | 成功反馈和去重 | 提示获得 ID、员工卡标记消失，同卡不能重复领取 |
| B-07 | 接手 CardManager | 在已有骨架中维护三卡、双槽和当前卡，关闭 UI 后数据仍在 |
| B-08 | 三卡双槽规则 | 首张 A、次张 B、第三张背包；最多佩戴两张且不丢卡 |
| B-09 | Q 与装备接口 | 实现 switch_active、equip_card，供 D 调用；一次输入不重复操作 |
| B-10 | 实际换卡通知 | 主动切换／装备成功发 identity_changed；普通刷新不冒充换卡 |
| B-11 | 一楼三名员工完整测试 | 三卡可依次获得，上楼条件可读取，1F 重试正确 |
| B-12 | 给 A 的组件交接 | 场景、脚本、公开配置、主角绑定和 F6 实测说明，可重复摆放 |

A 已创建 CardManager 的空数据读取、查询副本、重置和信号声明。B 在该文件继续开发，不重建一个同名管理器；“信号已声明”不代表切卡和装备已实现。员工和卡片有效操作当前仍待 B 制作。

## 5 C 的任务顺序和交付标准

| 编号 | C 要做什么 | 交付物与完成标准 |
|---|---|---|
| C-01 | 建通用房门 | monster_door.tscn，有门号和占位怪物图 |
| C-02 | 三状态循环 | 关闭约 5.5 秒 → 预警 1.4 秒 → 开启 2.8 秒，稳定重复 |
| C-03 | 清楚的视觉预警 | 静音能辨认危险将至，开启显示怪物、关闭隐藏 |
| C-04 | 门前检测区 | 原型左右各 90 像素，远处及关闭／预警状态安全 |
| C-05 | 独眼客 | 开启且在范围时，只有当前保安卡安全 |
| C-06 | 长鼻和礼帽 | 同一代码按类型读取保洁／经理卡，不整份复制程序 |
| C-07 | 大耳客 | 开启且在范围时，移动失败、停步安全，卡片无效 |
| C-08 | 核验客 | 接 B 的实际换卡信号；开门且在范围时换卡失败，普通行走安全 |
| C-09 | 检查器配置 | 房号、类型、半径、三段时长、offset 可由 A 调整 |
| C-10 | 多门错相位和安全区 | 独立摆三门，计时稳定，能观察和等待，不制造必死重叠 |
| C-11 | 失败原因上报 | 使用 WRONG_CARD／MOVED_NEAR_EAR／SWITCHED_NEAR_CHECKER |
| C-12 | 五怪回归 | 正确／错误卡、开／关／预警、范围内外、停止和换卡都可重复验证 |
| C-13 | 给 A 的组件交接 | 一套门可复用到 2F—5F，附摆放、参数与测试说明 |

C 可以先完成计时、预警和无卡失败；“有保安卡安全”及实际换卡场景依赖 B 的操作接口。不得给 CardManager 只读属性强行赋值或另存一份假卡片数据来绕过依赖。

## 7 第一次小样及接入依赖

11 月 8 日前的最低交付是一段完整可玩的测试闭环，不要求五层全完成。

| 成员 | 小样交付 | 验收动作 |
|---|---|---|
| A | 共同底座、主角、组装测试区 | 菜单可进入，人物移动，员工和门在主游戏可用 |
| B | 一名转身保安、保安卡收集 | 背后成功，正面／中途回头失败 |
| C | 一扇三状态独眼门 | 无卡失败、有保安卡安全、关闭／预警安全 |
| D | 开始菜单、失败页、一页说明 | Start 和 Retry 能触发 A 的正确流程 |
| 全员 | 一套临时素材、组件交付 | A 发布可运行小样，D 录短视频 |

依赖顺序：A 公共底座与接口 → B/C/D 独立制作 → A 先接 B、再 C、最后 D → 全流程回归。C 的卡片验证与 D 的装备按钮依赖 B，D 的失败／重试按钮依赖 A 的流程入口。

如果某项 UI 或样式暂时接不上，先用明确标识的临时提示保住流程，并登记未完成项。不能用“代码已写完”代替可运行小样，也不把未验证功能写成通过。

## 10 组件提交和仓库管理

每个组件独立保存 .tscn，成员先 F6 验证，再检查自己分支的改动范围、Commit、Push、提 PR；主场景和项目设置由 A 统一维护。PR 写明做了什么、怎么运行、实际测试、需要 A 接哪里、证据和未完成项。

A 看文件范围、接口和 Godot 运行结果，通过后合入 main；全员将最新 main 同步回自己的分支。当前沿用长期个人分支，普通 merge commit 和具体 Desktop 操作以协作指南为准。成员组别与分支的对应关系由 A 明确，不由文档猜测。

QA 由 D 组织：每条 BUG 写楼层／房号、前置状态、操作、实际／预期、负责人和证据；修复后重复原步骤，必要时三次复测，并回归关联用例。

AI 每次只改清楚的模块范围，读取 AGENTS 和公共接口，说明实际验证。遇到报错先修相关文件，不重写整个项目。模板在协作指南，函数签名以接口文档为准。

## 11 最终交付和延期取舍

必须交付：可运行游戏、GitHub 源项目、操作说明、截图、演示视频；四人都负责一段可运行 Godot 功能，全员至少完整试玩一次。Windows 优先与课程平台确认沿用主策划，基础完成后分别进行 Windows/macOS 试玩，导出包另外验收。

延期时先减少走路／怪物动画、装饰、随机相位、复杂声音、多页剧情和华丽背包效果。保留主角移动、背后偷卡、三卡双槽、五怪、清楚预警、救援、出口和本层重试。最终逐项检查主策划范围及 QA 的 T01—T14，不能因素材漂亮跳过功能验证。

当前下一步是成员取得云端底座、核对版本并完成自己的第一份组件交付。基础脚本、独立测试、Mac 画面与干净源码导入的证据在进度记录；成员电脑、Windows 导出和主线验收尚未通过。
