## 如何记录测试

状态统一使用“未执行、通过、失败、待确认”。通过必须有实际操作和观察结果；待确认用于行为要求尚未决定的情况。

每次测试记录：日期与时区、测试人、操作系统、Godot 准确版本、分支／提交或未提交文件范围、场景、用例编号、实际结果及证据位置。变更修复后重测原条件；相同 BUG 建议重复三次，并回归受影响功能。

截图、日志或短视频按需保存到团队选定的位置，记录相对路径或链接。不要为尚未录制的材料填写虚构证据。

## 历史 V3 补充检查（已由 V4 用例接续）

- 偷卡重复获取、正面／背面的范围边界、偷窃中途移动和松开 E。

- 多扇门同时失败时只处理一次；重试后输入恢复且门相位正确。
- 1F 重试清空本轮获取；3F 救人后的本层重试；装备快照的恢复方式。
- 背包、手册、暂停时门计时与输入如何处理，以及暂停界面按钮如何响应。
- 静音时预警可见，五怪不能只靠颜色辨认，走廊具有可退回的安全空间。

这些是后续验证方向。背包、暂停和详细交互的期望结果由组长在对应功能阶段确认后填写，不作为基础环境任务的前置门槛。

## BUG 记录格式

复制下表填写，一条 BUG 对应一个可重复的问题。当前没有已登记的游戏 BUG；功能未实现不登记为运行 BUG。

| 字段 | 填写内容 |
|---|---|
| 编号与标题 | 如 `BUG-001`，用一句话说明具体问题 |
| 环境 | 日期、系统、Godot 版本、分支／提交或未提交范围 |
| 位置 | 场景、楼层、房号或界面 |
| 前置条件 | 已有卡、当前卡、故事进度、门状态等 |
| 复现步骤 | 按发生顺序写出具体操作 |
| 实际结果 | 亲眼看到的现象及错误日志 |
| 预期结果 | 对应规则或用例编号；未定规则标记待确认 |
| 证据 | 截图、日志、视频路径或链接 |
| 影响与负责人 | 是否阻塞启动／通关；交给 A/B/C/D 中谁 |
| 状态 | 待处理／修复中／待复测／已关闭 |
| 复测 | 测试人、日期、相同条件结果及关联回归用例 |

修复者提供修改与自测结果，复测者确认原问题消失后再关闭。
